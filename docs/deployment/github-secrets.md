# GitHub Secrets — exact list

Add these under **Settings → Environments → production → Environment
secrets** (preferred, scopes them to the `production` GitHub environment
that `deploy-production.yml` targets, letting you also require a manual
approving reviewer there) — or under **Settings → Secrets and variables →
Actions → Repository secrets** if you don't want the approval gate.

## Deploy transport (password-based, no SSH key)

| Secret | Value | Notes |
|---|---|---|
| `VPS_HOST` | `149.202.34.65` | |
| `VPS_PORT` | `22` | Optional — the workflow defaults to `22` if unset. |
| `VPS_USER` | `ubuntu` | |
| `VPS_PASSWORD` | *(the VPS password)* | Never pasted into chat/repo/logs. GitHub masks it automatically once stored as a secret. |
| `VPS_DEPLOY_PATH` | `/opt/mzali/releases/mzali` | The persistent git checkout on the VPS that `deploy-production.yml` `git fetch`/`git checkout`s inside. |

Registry auth reuses `github.actor` + the built-in `secrets.GITHUB_TOKEN` —
matching the existing `cd.yml` pattern, no separate `GHCR_USERNAME`/
`GHCR_TOKEN` secret is needed unless your org's GHCR policy specifically
requires a PAT (some orgs restrict `GITHUB_TOKEN`'s package-write scope —
if `docker/login-action` fails with a permissions error, create a
classic PAT with `write:packages` and add it as `GHCR_TOKEN`, then swap
`password: ${{ secrets.GITHUB_TOKEN }}` for `password: ${{ secrets.GHCR_TOKEN }}`
in `deploy-production.yml`).

## Application secrets — NOT stored in GitHub Secrets

Every value below lives **only** in `/opt/mzali/shared/.env.production` on
the VPS (`chmod 600`, symlinked into the repo checkout as `deploy/.env` —
`deploy-production.yml` does this automatically on first deploy). This is
deliberate: application secrets don't need to pass through GitHub Actions
at all, since the deploy script runs *on* the VPS and reads them from disk
there. Populate this file from `deploy/.env.example`:

```
GHCR_OWNER, IMAGE_TAG, COMPOSE_PROJECT_NAME
STOREFRONT_DOMAIN, WWW_DOMAIN, ADMIN_DOMAIN, POS_DOMAIN, API_DOMAIN, MEDIA_DOMAIN
MINIO_PUBLIC_URL, CADDY_ACME_EMAIL
NEXT_PUBLIC_SITE_NAME, NEXT_PUBLIC_SITE_URL, NEXT_PUBLIC_CURRENCY_CODE, NEXT_PUBLIC_CURRENCY_SYMBOL
COMMERCE_PROVIDER, SESSION_SECRET, JWT_ACCESS_SECRET, SERVICE_TOKEN
CORS_ORIGINS                              # optional, empty by default — see the audit doc §7
MONGO_INITDB_ROOT_USERNAME, MONGO_INITDB_ROOT_PASSWORD, MONGO_REPLICA_KEY, MONGODB_URI
REDIS_PASSWORD, REDIS_URL
MINIO_ROOT_USER, MINIO_ROOT_PASSWORD
ACCESS_TOKEN_TTL_MINUTES, REFRESH_TOKEN_TTL_DAYS, SESSION_ROLLING_ENABLED,
AUTH_PROACTIVE_REFRESH_SECONDS, STRICT_STOCK
NAVEX_API_BASE, NAVEX_TOKEN_ADD, NAVEX_TOKEN_GET, NAVEX_TOKEN_DELETE, NAVEX_AUTO_PUSH_LABEL
FIRST_DELIVERY_API_BASE, FIRST_DELIVERY_TOKEN, FIRST_DELIVERY_AUTO_PUSH_LABEL
AXESS_API_BASE, AXESS_TOKEN, AXESS_ENTREPOT_ID, AXESS_SOURCE_NOM, AXESS_SOURCE_TEL,
  AXESS_SOURCE_ADDRESS, AXESS_SOURCE_GOV, AXESS_SOURCE_DELEGATION, AXESS_SOURCE_LOCALITE
BACKUP_TARGET, BACKUP_RETENTION_DAYS, RESTORE_MONGODB_URI, SMOKE_PRODUCT_PATH
```

**Not applicable to this codebase (do not add — nothing reads them):**
`SMTP_*` (no email sending exists anywhere in the system), `NEXTAUTH_SECRET`
(auth is custom JWT + HMAC-signed cookies, not NextAuth), `COOKIE_SECRET`
(the actual name is `SESSION_SECRET`, already listed above), payment
gateway secrets (COD-only, no payment integration exists). See the audit
doc for how I confirmed each of these.

## Generating strong secret values

```bash
openssl rand -hex 32          # SESSION_SECRET, JWT_ACCESS_SECRET, SERVICE_TOKEN
openssl rand -base64 756 | tr -d '\n'   # MONGO_REPLICA_KEY
openssl rand -base64 32       # MONGO_INITDB_ROOT_PASSWORD, REDIS_PASSWORD, MINIO_ROOT_PASSWORD
```

Every secret must be **independent** — do not reuse one password for
multiple services.

## Rotating the VPS password

Since deployment authenticates with a password (by your explicit choice,
not an SSH key), rotate it periodically:

1. On the VPS: `sudo passwd ubuntu` (you'll be prompted for the current
   password, then the new one twice).
2. Immediately update the `VPS_PASSWORD` GitHub Secret to match — until you
   do, CD will fail to authenticate (fails safely: it just can't connect,
   nothing is left half-deployed).
3. Trigger a manual `workflow_dispatch` run of `deploy-production.yml` to
   confirm the new password works end-to-end before you consider the
   rotation complete.

## Rotating application secrets

Application secrets are edited directly on the VPS
(`/opt/mzali/shared/.env.production`), never regenerated by the deploy
pipeline. To rotate one (e.g. `JWT_ACCESS_SECRET`):

1. `nano /opt/mzali/shared/.env.production`, change the value.
2. Restart the affected services: rotating `JWT_ACCESS_SECRET` invalidates
   every existing session (admin, POS, employee) — expect everyone to be
   logged out.
   ```bash
   cd /opt/mzali/releases/mzali
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml -f deploy/docker-compose.prod.yml up -d
   ```
3. This does **not** go through CI/CD and does not change `IMAGE_TAG` — it's
   a config-only restart, containers keep running the same images.
